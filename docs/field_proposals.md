# Field observations and the updates derived from them

**Status: the proposals in section 3 were applied to `docs/fields.json`** (descriptions, `hdr.u48` and `record.ngp_tutorial` -> `likely`, read-only `item.key_num` / `item.entry_number`, `observed_values` for `mission.progress`). Not applied: the optional tighter range 0..4 for `player.current_film_slot` (it could block a valid value). Nothing became `confirmed`. Section 4 lists doc fixes applied alongside.

**Observed in 42 unique user saves, uncontrolled.** Other players' saves, no experiment: this data can narrow hypotheses and show which values occur, but it can never make a field `confirmed`. Groups are anonymous sources plus the uploader's set tag (a hint, not proof). Generated by `tools/field_report.py` from `tools/corpus.py`, `tools/field_stats.py`, `tools/correlate.py`. Sections 1 and 2 are the evidence as computed before the update.

## 2. Candidate fields and the evidence for them

| candidate | evidence (observed counts) | reading |
|---|---|---|
| header 0x48 (`hdr.u48`) = `current_end_` + 10 x `difficulty_clear_flag_[3]` + 100 x `is_new_game_plus_tutorial_compl` | formula reproduces the header value in 42/42 saves; the tens digit matches flag [3] in 42/42 but flags [0], [1], [2] only in 29, 31, 35; only 6 distinct values occur | a packed 'completion code' copied to the header (the exe's writer computes `a + 10*b + 100*c` from three fields, which I read earlier). Strong fit, but only 6 combinations were seen |
| header 0x38 (`hdr.u38`) | 3 in 35/42 saves (all of player A, B, D); 0 in 7/42 (all of player C and `me`); every save with `difficulty_clear_flag_[3]` set has 3 (11/11); every save with flag [0] set has 0 (2/2) | possibly the difficulty index of the playthrough (0 where flag [0] was set, 3 where flag [3] was set). Not independent of the uploaders' labels: **a candidate, not a result** |
| `lap_num`, `last_selected_lap_num_`, header 0x1C | = 1 in 42/42 saves, including 12 labelled NG+ practice, 3 from the uploader folder named NG+, and the 100% / all-unlocked saves; 0 saves have a value other than 1 | **no evidence this is the NG+ lap counter.** Either it is not that, or none of these saves is in a later lap |
| `senki` vs `sen` | equal in 42/42 saves (0..56,525) | mirror fields; still cannot tell which one the game reads (experiment 1) |
| `current_end_` | values: 0 in 29, 1 in 9, 5 in 4. 5 in both 100% / all-unlocked saves and in 2 of player B's NG+ practice saves; 0 in all 21 nightmare-practice saves. The ones digit of header 0x48 equals it in 42/42 | plausibly a clear / ending counter (name + 5 in 100% saves); semantics untested |
| `is_new_game_plus_tutorial_compl` | True in 6/42 saves, **always** with `current_end_` >= 1 (True in 6/13 saves that have a clear, never True with `current_end_` = 0). The hundreds digit of header 0x48 equals it 42/42 | consistent with 'NG+ tutorial shown after the first clear'; the meaning rests on the key name |
| `difficulty_clear_flag_` [0..3] | only these combinations occur: none set (x29), [3] only (x7), [0] only (x2, player C and `me`), [2]+[3] (x4, both 100% / all-unlocked saves and 2 of player B's); [1] never set | flags are per difficulty; their order/names unknown; 'clears recorded' is a reading from the key name |
| `unlock_amulet_slot_num` | 1 in 27 saves (all with no clear), 2 in 2 (player C and `me`: first clear, tutorial True), 4 in 13 (the 100% and all-unlocked saves plus 11 of player B's NG+ set, 2 of them with `current_end_` 0); 3 never | slots grow with clears / NG+ carry-over; max seen = 4 = schema max |

| `item_object_unique_number` | Spearman rho = +0.999 with progress inside player B's nightmare set (21 saves); but ordered by play time it is non-decreasing in only 176/210 pairs there and 19/66 pairs in player B's NG+ set | grows along one playthrough; **not** a globally monotonic counter |

## 5. PROPOSAL (not applied): `item.num` and item names

**Evidence limits first.** The new names and the layout of an inventory entry come from a community Cheat Engine table: third-party, from another game build (its own header says v2.02.02; a trainer for it says v1.02; ours is a different file), **not** a controlled experiment, and not yet checked against our exe (optional Step 3). It can support `likely`, never `confirmed`.

| field | current | proposed | reasoning | limits |
|---|---|---|---|---|
| `item.num` | guessed | **likely** | (1) the table's inventory code compares a 4-byte key at entry+0 with an item hash and reads/writes the quantity at entry+8 in 16-byte entries; our save lists `key`, `key_num`, `num`, `flag`, which would be offsets 0, 4, 8, 12; (2) in the 42 samples each key has at most one row per save, rows stay at 0 after use (4 of the nine named keys have such a row), and Type-14 Film is never below 14; (3) `key_num` is unique per row and varies per save, so it is not the count (docs/items_observed.md) | the layout match is a pattern match, not a proof; Prayer Beads (128-420, 99999) and key `0x7A5EBCFF` (99999) exceed the table's 99; the real per-item limits are unknown; saves with 99999 may be hand-edited; experiment 2 has not been run |
| `item.key` | guessed | **likely** (optional) | the table compares this dword with fixed hashes to identify items, which agrees with 'hash id' | same as above; says nothing about names |
| `item.num` max | 99999 | unchanged | 99999 is seen in 3 samples | no evidence of the real limit |
| item names (`docs/items.json`) | none | 9 names at `likely` + 2 unnamed (applied in Step 2) | third-party table | `confirmed` only via experiment 2 |

If you approve the two promotions I will apply them in one small commit; until then `fields.json` is unchanged.
