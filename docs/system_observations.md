# System save (SYSTEMSAVEDATA00): what the samples show

**Observed in 6 unique system saves of other players (7 files on disk, one duplicate), uncontrolled.** Nothing here was tested in the game; every system field in `docs/system_fields.json` is `guessed` and **read-only**, and the tools refuse to edit or write system saves. Labels: letters = anonymous sources; the part after `/` is the uploader's own tag for that file (a hint, not proof). Generated by `tools/system_report.py` from `tools/system_analysis.py`.

## 1. Container and structure

- Magic `WLNSYS`, size 61,851,984 bytes (payload 61,851,728). It decrypts with the **same AES-128-CBC key and IV** as user saves, and both checksums (0x50, 0x70) verify: **6/6 unique files, 7/7 files on disk, byte-exact round trip.**
- Header: 0x1C and every game-state field (0x20..0x48) are 0; only the magic, version, length, user-ID field, timestamp (0x30), the two checksums and the non-zero encrypted flag (0x4C) are filled. The plaintext starts with the same 16-byte prefix as user saves.
- JSON starts at plaintext offset 16 and is 392,034..415,349 bytes; the same 5 top-level sections and the same 21,853 leaf paths (all ints and bools) in all six saves.

| section | bytes (first save) | keys | leaf values |
|---|---|---|---|
| `SystemData` | 59,151 | 42 | 3,643 |
| `SystemUiData` | 59,329 | 1 | 2,653 |
| `SystemPlayerRecordData` | 46,404 | 15 | 2,885 |
| `PHOTO_SYSTEM` | 64,391 | 1 | 3,456 |
| `PHOTO_GHOST_LIST` | 185,981 | 1 | 9,216 |

- **After the JSON** the payload is zero padding and binary data whose amount differs a lot between saves; it is not decoded here:

| save | JSON bytes | non-zero bytes after JSON | first non-zero byte (plaintext offset) |
|---|---|---|---|
| A/- | 415,349 | 41,019,197 | 17613392 |
| B/NG+ | 415,280 | 41,035,869 | 17613392 |
| B/NIGHTMARE | 392,218 | 107,037 | 17613392 |
| B/STORY_NORMAL_BATTLE | 392,034 | 0 | none |
| B/nm-practice | 394,675 | 3,498,046 | 17613392 |
| C/- | 398,717 | 9,188,263 | 1024016 |

The first non-zero offset is 1,024,016 in one save (the same place user saves keep their binary tail), 17,613,392 in four, and none in one save that has no binary data at all. The meaning of these regions (photos?) is **unknown**.

## 2. What varies between the six saves

7,377 of the 21,853 leaf values differ in at least one save, almost all in photo / ghost-list data and in the unlock lists. Areas with the most differing values: ghost-list photos (4,891), per-ghost UI data (1,323), `ghost_list_unlock_data_` (375), `omamori_unlock_data_` (210), `document_unlock_data_` (121); then key bindings, `record_save_data` (49), futago/reiseki/chibarai/yobimodoshi lists, played-scene lists and settings.

- `shop_point_` is huge in the four advanced saves (up to 180 million) and 0 in the two freshest; whether it is a balance or a lifetime total is unknown. It is not the per-playthrough points of a user save.

- `costume_bit_flag_`, `photo_sticker_bit_flag_` and `photo_frame_bit_flag_` look like bit masks that are non-zero/full only in the fully unlocked saves (0x7FFFFFFF for stickers).
- The `setting_*` arrays are player options (language, audio volumes, graphics, key bindings, controller): they differ per player, not with progress.

- Every save's unlocks are a subset of the two fully unlocked saves' in 12 of 12 lists. The two fully unlocked saves (A and B/NG+) have **identical unlock sets in 12 of 12 lists**; they differ in only 321 of 21,853 values (mostly ghost-photo data, key bindings, graphics options and a few records). That is consistent with B's NG+ file having been built from the same fully unlocked save; it is not proof.
- Source B's saves nest into each other (freshest <= nightmare <= nm-practice <= NG+). Source C is a different player and does not nest inside B's nm-practice save (7 of 12 lists).

## 3. What is known and unknown

**Known (reproduced on all 6 unique files):** codec, both checksums, JSON structure, 108 leaf-path patterns, that the header holds no game state, that nothing in the JSON refers to the user ID.

**Guessed (all of `docs/system_fields.json`):** which list is which (names only), that the lists are sets of hashed ids in unlock order, that the bit flags are unlock masks, that the ending flags are per ending.

**Unknown:** what the hashed ids are (no name table), what the binary data after the JSON is, whether the game accepts an edited system save (never tested; editing is not supported), what `shop_point_` counts, how `record_save_data` (500 records, 62 filled in every save) is used, the meaning of 0x4C and the user-ID field in a system save (same rules as user saves are assumed).

## 4. Loading a 61 MB file (measured on macOS, CLI `info`, three runs each)

| file | wall time | peak memory |
|---|---|---|
| user save (9.3 MB) | 0.08 s | 97 MB |
| system save (61.9 MB) before trimming | 0.11 s | 304 MB |
| system save after sharing the read-only buffer | 0.12 s | 256 MB |

The system save is decrypted in about 0.1 s. The app does not decrypt it just to draw the slot list (only the 256-byte header is read), shows one summary row per list instead of thousands of rows, and the hex view is virtualized, so **no different loading approach is needed.** A byte-exact re-encryption (`verify --roundtrip`) needs about 490 MB because it holds a second copy.
